# Agent Note: 已配置视觉模型路由

Status: implemented

[English](2026-08-18-configured-vision-model-routing.md) | 中文

## 问题

图像理解插件绕过了应用的模型配置，直接调用单一的 Qwen 兼容接口。`qwen3.7-flash`、DashScope 地址和独立的凭据引用因此都属于插件自身设置，用户无法复用其他已配置的多模态提供方，也无法选择其他视觉模型。

## 决定

图像理解现在选择一个已启用的提供方路由，以及该路由中明确声明支持 `image` 输入的模型。插件卡片只保存 `visionProvider` 和 `visionModel`；提供方地址、API Key 和模型输入能力仍由“模型”设置页负责。

宿主模型目录现在会将 `inputModalities` 写入面向客户端的模型条目。视觉选择器只展示支持图片输入的模型，在设置或适配器变化时刷新，并在切换提供方时清除不兼容的模型草稿。执行时，`mcp__vision__analyze_image` 解析已保存的路由，拒绝缺失或纯文本的选择，然后通过 `ctx.llm` 流式发送提示和持久图片附件；它不再直接请求任何提供方接口，也不再读取插件专用密钥。

## 考虑过的替代方案

- **在模型选择器旁保留 Qwen 回退**——拒绝。隐式回退仍会将插件耦合到单一提供方，也会使界面显示的选择与实际接收图片的路由不一致。
- **在视觉插件中内嵌创建自定义提供方**——拒绝。“模型”页已经负责提供方定义、凭据和输入能力；复制该编辑器会为同一路由制造两条配置路径。
- **列出输入能力未知的模型**——拒绝。视觉工具不应展示无法证明可接受图片的选择。用户可在“模型”中定义自定义模型时声明图片输入能力。

## 后果

- 现有 Qwen 专用视觉设置不再能配置路由。此前使用它们的部署需要先在“模型”中添加所需提供方和支持图片输入的模型，再在视觉插件中选择它。
- 提供方只需配置一次模型标识和密钥，普通对话与图像理解会使用同一适配器、重试策略和传输行为。
- 未提供图片能力元数据的提供方会有意对图像理解不可用，直到该能力被声明。

## 测试

生图 MCP 测试覆盖将最新的持久用户图片路由到已配置视觉提供方，以及拒绝缺少视觉路由的情况。插件控制器测试覆盖过滤纯文本模型、成对选择的持久化和模型目录查询失败。宿主模型目录测试覆盖选择器依赖的 wire 合约。
