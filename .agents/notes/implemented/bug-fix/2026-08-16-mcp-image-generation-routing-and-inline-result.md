# Agent Note: MCP image-generation routing and inline result

Status: implemented

English | [中文](2026-08-16-mcp-image-generation-routing-and-inline-result.zh.md)

## Problem

The MCP image bridge submits its explicit prompt as a plugin-sourced user-role message, while the OpenAI Image API adapter accepts only direct-user messages to prevent injected runtime context from becoming an image prompt. The adapter therefore rejects the bridge before provider I/O. The tool schema also exposes only a prompt, so the caller cannot choose composition dimensions or quality for one request even though the adapter sends route-level defaults. A successful attachment is accompanied by a redundant tool row, so generated media does not read as the tool's immediate conversation result.

## Decision

`GenerateOptions.purpose` includes `image-generation` for one-shot auxiliary image calls. The MCP bridge sets that purpose and submits one plugin-sourced prompt. The Image API adapter accepts a plugin-sourced prompt only when this purpose is present; ordinary calls retain the direct-user requirement. `GenerateOptions.imageGeneration` carries request-level `size`, `quality`, and image count. The MCP schema requires the caller to choose dimensions and quality, allows a separate-image count, and the adapter merges these values over the route configuration while keeping response encoding route-owned.

The tool result keeps model-facing content textual and persists image references in presentation metadata. The Web image-generation renderer replaces a successful tool row with an always-visible gallery; running, failed, and malformed results keep the row so progress and diagnostics remain visible. `session.attachment` treats a complete image reference in the durable `tool/result` metadata `images` array as session-authorized, while rejecting incomplete lookalikes and unrelated metadata. Generated bytes therefore remain outside a text model's subsequent context while the user sees the media in the conversation.

## Alternatives considered

**Label the bridge prompt as a direct-user message.** This would make provenance false and allow code to bypass the adapter's distinction between submitted user input and injected context.

**Accept every plugin-sourced prompt in the Image API adapter.** Runtime snapshots and instruction injections also use plugin sources. Selecting them without an explicit auxiliary purpose would reintroduce the prompt-confusion check the adapter prevents.

**Return image blocks to the calling text model.** A generated attachment in `tool-result` content would enter later model requests and fail on text-only routes. Presentation metadata keeps the durable reference available to the Web client without changing model history.

**Append an additional assistant message.** Assistant messages require model provenance and occupy the agent loop's step sequence. A tool cannot fabricate that event without misrepresenting ownership or changing loop semantics.

**Encode dimensions and quality only in prompt prose.** Words such as “8K” or “high quality” describe image content but do not set Image API wire fields. Typed request controls preserve provider defaults for omitted fields and make the actual request inspectable.

## Consequences

The MCP bridge reaches the configured Image API while ordinary plugin context remains ineligible as an image prompt. Each MCP generation selects an explicit layout and quality, and both generation JSON and edit multipart requests receive the same overrides. Web users see generated images immediately without a successful-call label, including after replaying an existing session; non-Web clients retain the textual completion and durable metadata. The inline gallery is presentation-only and does not increase text-model context size.
