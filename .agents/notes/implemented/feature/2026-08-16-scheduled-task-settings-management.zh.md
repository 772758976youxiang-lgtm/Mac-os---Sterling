# Agent Note: 定时任务设置管理

Status: implemented

[English](2026-08-16-scheduled-task-settings-management.md) | 中文

## 问题

Schedule 提醒已经持久化且可由模型管理，但用户无法在设置中查看 live 会话将要执行的内容。创建或修正提醒需要再发起一个模型轮次，删除提醒还需要知道其会话本地 id。全局设置文档可以简化行枚举，却会在会话事件日志之外产生第二个权威，并可能与 dispatch 状态分歧。

## 决策

设置外壳以顺序 12 注册独立的 `ui-settings-schedules` 客户端插件，位于「模型」和「插件」之间。页面列出活动提醒的归属会话、周期、下次目标与交付状态，并提供本地化的创建、编辑、删除确认、加载、空白、失败和忙碌状态。一次性表单输入使用浏览器本地 `datetime-local` 值，并发送 UTC RFC 3339 时点；周期规则仍是 Schedule 协议中至少 5 分钟的固定间隔。

`ScheduleService` 为既有模型工具与新的 Host API 共同拥有管理行为。它跟踪已经挂接 Schedule 运行时的 live 根 agent，在既有 Agent-scoped 事务队列中将所有调用与到期交付串行化，在持久化 preflight 后折叠会话日志，并在确认读取或变更后要求 timer 重新计算。`schedule.list/create/update/delete` RPC 领域把失败收容为业务值，并为每个活动视图加入归属会话 id。

编辑是替换，而不是新的持久事件形状。在同一个受管事务中，服务会确认旧 id 仍然活动、分配一个永不复用的新 id、依次追加 delete 与 create，并对组合追加执行一次变更后持久化 barrier。编辑期间页面固定归属会话。成功变更会刷新完整目录；连接重置与手动刷新负责覆盖外部变更。

目录有意只覆盖已挂接的 live 根 owner。列表读取不会恢复 cold 会话，因为仅为查看设置而恢复会话，可能立即准入 overdue 工作并启动模型轮次。cold 会话中的持久提醒会在该会话再次 live 后显示。

## 已考虑的替代方案

**把任务行存入设置。** 这样容易实现全局枚举，却会复制 Schedule 状态，需要与 `schedule/change` 对账，还可能报告已经由 dispatch 或回放终结的任务。

**列出时恢复所有会话。** 这样能显示 cold 提醒，却会让读取改变行为：overdue 工作可能执行、模型资源可能被获取，大量休眠会话也可能变为 live。

**增加持久 update 事件。** 第四种变更形状需要修改版本化 decoder、回放、持久化和 invariant。delete 加 create 已能表达替换，同时保留 id 不复用规则与既有事件语法。

**从浏览器调用模型工具。** 工具执行属于模型轮次范围，并使用面向模型的 snake_case 输入与展示。类型化 Host RPC 让人类 UI 管理独立于工具调用历史，同时复用相同的服务实现。

## 验证

Schedule 测试固定替换顺序、id 分配、持久化检查点和最终活动折叠。Host API 类型检查覆盖请求与响应 schema 以及 fixture 分发。客户端测试覆盖列表投影、领域与传输失败、写后刷新、设置注册与本地化、周期校验，以及创建、编辑与确认删除交互。浏览器验证在桌面和移动端宽度下检查组装后的 fixture 页面。

## 后果

- 用户无需花费模型轮次或处理 Schedule id，即可检查和管理定时工作。
- 会话日志仍是唯一持久权威；设置页不存储任务副本。
- 编辑会为任务分配新 id，并为组合替换保留持久化不确定性语义。
- cold 会话提醒在其会话再次 live 前不会出现在目录中；设置读取不会产生 agent 激活副作用。
- 其他标签页中的变更需要手动刷新或连接重置，因为 Schedule 不发布客户端失效事件帧。
